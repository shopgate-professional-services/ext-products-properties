## Project Overview

Shopgate Connect app extension that renders configurable product properties into
theme portal positions (product detail page, product tiles, favorites, cart) and
widens the set of properties the catalog pipelines return. Everything is driven by
merchant configuration from the Connect Admin; no merchant-specific code lives here.

## Tech Stack

Two independent npm packages with no root `package.json`. They do not share tooling.

- `extension/` — backend pipeline steps. CommonJS, runtime dependency
  `@shopgate/bigapi-requester`. Lint via the `standard` CLI, tests via mocha and
  node `assert`.
- `frontend/` — React 17 portal components. ES modules and JSX, `react-redux` 8,
  `reselect` 4, `glamor` for styles. Lint via `eslint` 8 with
  `@shopgate/eslint-config`, tests via jest from `@shopgate/pwa-unit-test`.

## Common Commands

Run these from inside one of the two package directories — there is no root package.

Backend (`extension/`), from `extension/package.json` and `.travis.yml`:

```
npm install
npm t              # mocha --use_strict --recursive test/unit
npm run standard   # standard CLI
npm audit
```

Frontend (`frontend/`), from `frontend/package.json`:

```
npm install        # not stated in any repo file, but required for the devDependencies
npm run lint       # eslint, uses the root .gitignore as its ignore file
npm test           # jest, config re-exported from @shopgate/pwa-unit-test
```

Neither half has a build step; the theme builds the frontend. Nothing in this
repository documents how to run the extension locally against a shop — verify the
platform SDK workflow elsewhere before relying on it.

## Repository Structure

- `extension-config.json` is the wiring. `components[].path` points at a directory
  under `frontend/portals/` whose name equals the component `id`; `steps[].path`
  points at one backend file plus the pipeline hooks it attaches to. Nothing in
  this repository reads that manifest — the platform tooling does.
- **A portal component is mounted once per target position.** The position name
  arrives as the `name` prop and is the only way the component knows where it is;
  `useTargetConfigs(name)` filters the admin config by it.
- The four `frontend/portals/*/index.jsx` files are near-identical and differ only
  in the connector they are wrapped in. Changing one usually means changing all four.
- Backend entry points are the four step files at the root of `extension/`, each
  `async (context, input) => output`. Everything else there is a helper reached by
  `require`; `extension/api/` isolates the network client.
- `frontend/properties/` is the data layer (`selectors`, `connectors`, `hooks`,
  `helpers`), `frontend/components/` is presentational. There are two unrelated
  helper modules: `frontend/helpers/index.js` and `frontend/properties/helpers.js`.
- Reading order: backend `extension/helpers.js` → `addProperties.js`; frontend
  `properties/hooks.js` → `properties/selectors.js` → a portal → `components/`.

## Local Development Notes

- `extension/config.json` and `frontend/config.json` are generated by the platform
  tooling from the manifest `configuration` block. Both are gitignored and absent
  from a fresh checkout, yet both are hard import targets:
  `extension/api/getApiClient.js` requires its copy **at module load**, and
  `frontend/properties/hooks.js` imports its copy as a default import. Any backend
  file that transitively reaches `getApiClient` cannot be required without it.
- `extension/.npmrc` pins the `@shopgate` scope to an internal Sinopia registry over
  plain HTTP, so installing `extension/` needs access to that host. `frontend/` has
  no `.npmrc` and resolves `@shopgate/*` from the default registry. No lockfiles are
  committed anywhere, so installs are unpinned.
- The `productsProperties` admin key has `destination: both`. The backend folds
  every configured `properties` entry into its own fetch list, so changing the
  frontend display config also changes backend behaviour.

## Testing Notes

- Backend: mocha, files at `extension/test/unit/<subject>-test.js`.
- Frontend: jest, co-located `*.spec.js`.
- `extension/helpers.js` caches its parsed config in module scope — the first config
  seen in a process wins for the process lifetime. Tests must bust the require
  cache; only `helpers-test.js` does.
- Two backend suites are broken as inherited, independent of any current work.
  `addProperties-test.js` passes `addProperties` as a CSV string that the
  implementation no longer splits, so several cases fail.
  `addPropertiesToCartItems-test.js` cannot be loaded at all, because it reaches the
  generated `config.json`, and its fixtures omit the `type: 'product'` field the step
  filters on. Do not assume a red backend suite was caused by your change.

## Deployment / CI Notes

- `.travis.yml` is the entire pipeline: Node 8, then `npm audit`, `npm t` and
  `npm run standard` — **all three scoped to `extension/`**.
- `frontend/` is not installed, linted or tested by CI. Run its lint and tests
  yourself before opening a pull request.
- `npm run standard` does not currently pass: several backend files carry semicolons
  and trailing whitespace that `standard` forbids.

## Project-Specific Pitfalls

- The extension `id` carries no `ext-` prefix (`@shopgate-project/products-properties`);
  only the repository is named `ext-…`. Keep `name` in both `package.json` files
  identical to the manifest `id`.
- The version is stated three times — `extension-config.json`, `extension/package.json`
  and `frontend/package.json`. Keep them in sync.
- `CHANGELOG.md` documents released versions only.
- The two halves match property labels differently: the backend lowercases before
  comparing but stores the original casing, while the frontend compares
  case-sensitively. A label matching in one half may not match in the other.
- `addPropertiesWithPrefix` matches with `includes`, not `startsWith`, despite the name.
- `frontend/components/ProductProperties/index.jsx` returns `null` unless the config
  entry sets `format`, `html` or `use_default_layout` — an entry with only `target`
  and `properties` renders nothing.
- The README config example uses `product.priceInfo.after`, but the registered target
  is `product.price-info.after`. Targets are matched by exact string, so a config
  copied from the README silently renders nothing.
- `frontend/helpers/index.js` imports `intl-messageformat`, which is declared in
  neither `package.json` and only resolves transitively.

## Editing Guidelines for AI Agents

- Never commit `extension/config.json` or `frontend/config.json`; both are generated.
- Import the generated frontend config as a **default** import including the `.json`
  extension — named imports from JSON are rejected by the lint config.
- A portal directory name must stay identical to its `id` and `path` in
  `extension-config.json`.
- Adding a target position means editing `extension-config.json` **and** the target
  list in the README, which is already incomplete.
- In `frontend/properties/connectors.js`, the selector factory must stay per
  connected instance, otherwise reselect memoization is defeated.
- The two halves have different linters and different style rules. Match the half
  you are editing; do not restyle the other one.
